# Спека: этап 0 «Фундамент»

Версия от 2026-11-20. Для кодинг-агента. Основание — `plan.md`, раздел «Технический фундамент», и технические правила проекта. Нарушение любого правила из раздела «Жёсткие правила» = переделка.

Срок: 3–4 дня при 15–20 часах в неделю. В «прототип через 2 недели» не входит.

## 1. Цель и решение игрока

Геймплея на этом этапе нет, и добавлять его нельзя. Решений игрока тоже нет. Цель — каркас, на который прототип ядра (этап 1) кладёт механики без переделок:

- ядро симуляции живёт отдельно от рендера и одинаково крутится в игре и в headless;
- любая партия воспроизводится по «сид + лог команд» бит в бит;
- мир меняется только командами из одного списка;
- 100 партий гоняются одной командой в терминале и дают отчёт;
- в репо лежит CLAUDE.md, который держит эти правила для следующих агентов.

Чтобы было что гонять и что рисовать, в ядре есть одна **отладочная система `DebugPaint`**: каждый тик красит случайные пиксели случайным владельцем. Это не механика и не баланс, её выключат и удалят в прототипе.

## 2. Жёсткие правила

1. Ядро — сборка `BattlePix.Core` на чистом C#: без `MonoBehaviour`, `ScriptableObject`, `GameObject`, сцены и любого `UnityEngine.*`. Разрешены только `Unity.Collections`, `Unity.Jobs`, `Unity.Burst`, `Unity.Mathematics` (только целочисленные типы) и `System` без `System.Random`, `DateTime`, `Stopwatch`, `Environment.TickCount`.
2. В ядре нет `float`, `double`, `decimal`, `Mathf`. Дробные величины — целые с фиксированным масштабом (проценты — в базисных пунктах, 10 000 = 100%). Деление округляет к нулю, это и есть правило.
3. Случайность только из своего генератора (PCG32, раздел 4.3). `UnityEngine.Random` и `System.Random` запрещены везде, где результат влияет на симуляцию.
4. Мир меняется только командами из `CommandType`. У ИИ (появится позже) нет других путей в мир, кроме тех же команд.
5. Порядок обработки фиксирован: никаких итераций по `Dictionary`/`HashSet`, где важен порядок, никаких параллельных редукций с недетерминированным порядком. Джобы пишут только в непересекающиеся индексы.
6. Рендер только читает состояние, и только между тиками. Одна `Texture2D` владельцев + палитра в шейдере, никаких GameObject на пиксель.
7. Нации, конфиг симуляции и ручки — в данных (JSON), не в коде.
8. UI — только тап: никаких подсказок «по наведению», цели нажатия не меньше 44×44 pt.
9. Симуляция считается на CPU, GPU только рисует.

## 4. Данные

### 4.1. Состояние мира (`World`, ядро, `IDisposable`)

| Поле | Тип | Что это |
| --- | --- | --- |
| `Width`, `Height` | `int` | 512 и 256, из конфига |
| `Owner` | `NativeArray<byte>` (Persistent) | владелец пикселя, индекс `y * Width + x`; 0 — ничей, 1..255 — id нации |
| `Terrain` | `NativeArray<byte>` (Persistent) | тип рельефа; на этом этапе везде 0 |
| `Nations` | `NativeArray<NationState>` | по одной записи на нацию, индекс = id − 1 |
| `Tick` | `int` | номер следующего тика, старт с 0 |
| `Rng` | `RngStreams` | состояния всех потоков генератора |
| `IsOver` | `bool` | партия закончена |
| `EndReason` | `EndReason : byte` | `None`, `TickLimit`; прототип добавит `Victory`, `Defeat` |
| `DirtyRowMin`, `DirtyRowMax` | `int` | диапазон строк, изменённых с последнего чтения рендером; −1, если изменений нет |

`NationState` — `struct { byte Id; byte Alive; }`. Золото, армии, столица и всё остальное добавит спека прототипа, сюда не класть.

`Owner` и `Terrain` наружу отдаются только как `NativeArray<byte>.ReadOnly`. Пишут в них только системы ядра.

### 4.2. Конфиг (`Assets/StreamingAssets/Data/sim_config.json`)

```json
{
  "format": 1,
  "width": 512,
  "height": 256,
  "ticksPerSecond": 10,
  "maxTicksPerFrame": 8,
  "checkpointInterval": 600,
  "commandHorizonTicks": 100,
  "debugPaint": { "enabled": true, "pixelsPerTick": 64, "nations": 8 }
}
```

`nations_debug.json` — массив `{ "id": 1, "name": "Debug 1", "color": "#C8553D" }` на 8 наций. Цвет нужен только палитре рендера, ядро его не читает.

Ядро получает конфиг как строку JSON и парсит Newtonsoft в DTO с целыми полями. Чтение файла — забота адаптера (игра читает StreamingAssets, на Android через `UnityWebRequest`; раннер читает с диска). `DataHash` — FNV-1a 64 по байтам всех файлов `Data/` в порядке сортировки путей.

### 4.3. Генератор (`Pcg32`, `RngStreams`)

PCG32 (вариант XSH RR, как в эталонной pcg-c): состояние `ulong state`, `ulong inc`.

- Инициализация `Pcg32(ulong initState, ulong initSeq)`: `state = 0; inc = (initSeq << 1) | 1; Next(); state += initState; Next();`
- `uint Next()`: `old = state; state = old * 6364136223846793005 + inc; xorshifted = (uint)(((old >> 18) ^ old) >> 27); rot = (int)(old >> 59); return (xorshifted >> rot) | (xorshifted << ((-rot) & 31));`
- `int NextInt(int boundExclusive)`, bound > 0: `threshold = (uint)(-bound) % bound`; тянуть `r = Next()`, пока `r < threshold`; вернуть `r % bound`. Без перекоса.

**Потоки.** У каждой системы свой поток, чтобы новая система не сдвигала случайность старых. `RngStreams` создаётся из сида партии: поток с номером `streamId` — это `new Pcg32(seed, streamId)`. Номера фиксированы в `enum RngStream : ulong { MapGen = 1, Front = 2, Debug = 3, Ai = 4, Events = 5 }` и никогда не перенумеровываются, только дописываются.

Сид партии — `ulong`, любое значение, включая 0.

### 4.4. Команды

```csharp
public enum CommandType : byte { Noop = 0, DebugSetOwner = 1 }

public struct Command {
    public int Tick;        // тик, в который применяется
    public byte Nation;     // кто отдал; 0 — система/отладка
    public int Seq;         // порядковый номер внутри тика, присваивает очередь
    public CommandType Type;
    public int A, B;        // параметры; для DebugSetOwner: A = индекс пикселя, B = новый владелец
}
```

Боевые команды из плана (ударить по фронту, крепость, набрать армию, объявить войну, предложить мир) **не** добавлять — их вводит спека прототипа. Enum только дописывается, значения не переиспользуются.

`CommandQueue.Enqueue(cmd)` принимает команду, если `World.Tick <= cmd.Tick <= World.Tick + commandHorizonTicks`. Команда из UI всегда ставится на `World.Tick + 1`, а не в текущий тик: так игра и реплей идут одинаково при любой частоте кадров. Каждая принятая команда пишется в лог, и неважно, пройдёт ли она потом валидацию: валидация детерминирована, и в реплее команда отклонится так же.

### 4.5. Реплей (`Replays/<дата>_<сид>.json`)

```json
{
  "format": 1,
  "build": "0.0.1+<git sha>",
  "seed": 42,
  "dataHash": "0x…",
  "ticks": 24000,
  "commands": [ { "t": 12, "n": 0, "s": 0, "type": "DebugSetOwner", "a": 128143, "b": 3 } ],
  "checkpoints": [ { "t": 600, "h": "0x…" } ]
}
```

Это и есть баг-репорт: сид + лог команд + контрольные хеши.

### 4.6. Хеш состояния

FNV-1a 64 (offset `0xcbf29ce484222325`, prime `0x100000001b3`) по байтам в таком порядке: `Tick` (4 байта, little-endian), `Owner`, `Terrain`, все `NationState` побайтно, состояния `state` и `inc` всех потоков в порядке `RngStream`, `IsOver`, `EndReason`. Считается Burst-джобом `HashJob : IJob`; рядом лежит managed-версия `HashManaged` для теста сверки. Контрольная точка — хеш после каждого тика, кратного `checkpointInterval`, и после последнего.

## 5. Правила и пример тика

### 5.1. Порядок тика (`Simulation.Step()`)

1. Если `IsOver` — ничего не делать.
2. Достать из очереди команды с `Tick == World.Tick`, отсортировать по `(Nation, Seq)`, провалидировать и применить по одной. Невалидную (пиксель вне карты, владелец больше числа наций) пропустить и записать в лог ядра как отклонённую.
3. Прогнать системы из `SystemPipeline` в фиксированном порядке. На этом этапе там одна `DebugPaint`, если она включена в конфиге.
4. `Tick += 1`.
5. Если `Tick % checkpointInterval == 0` — посчитать хеш и записать контрольную точку.
6. Если задан лимит тиков и `Tick == limit` — `IsOver = true`, `EndReason = TickLimit`.

Системы реализуют `interface ISimSystem { void Tick(World world, CommandContext ctx); }`. Порядок систем — данные пайплайна, а не порядок регистрации в рантайме.

**`DebugPaint`:** `pixelsPerTick` раз подряд из потока `Debug`: `x = NextInt(Width)`, `y = NextInt(Height)`, `owner = 1 + NextInt(nations)`; `Owner[y * Width + x] = owner`; расширить `DirtyRowMin/Max` на `y`.

### 5.2. Пример на одном тике

Сид 42, `pixelsPerTick = 1`, `nations = 8`, команд нет, все пиксели 0.

- Поток `Debug` = `Pcg32(42, 3)`.
- `NextInt(512)`: `Next()` = 1 594 523 791, порог 0, `x = 1594523791 % 512 = 143`.
- `NextInt(256)`: `Next()` = 976 819 194, `y = 250`.
- `NextInt(8)`: `Next()` = 2 272 355 874, `owner = 1 + 2 = 3`.
- Индекс `250 * 512 + 143 = 128 143`, `Owner[128143] = 3`, `DirtyRowMin = DirtyRowMax = 250`, `Tick = 1`.
- После тика `state` потока `Debug` = `0xabc2017ac9febb95`.

Второй тик с тем же сидом даёт пиксель `(450, 237)`, индекс 121 794, владелец 6. Эти числа посчитаны эталонной реализацией PCG32 и входят в тесты.

Эталон генератора: `Pcg32(42, 54)` выдаёт первыми `0xa15c02b7, 0x7b47f409, 0xba1d3330, 0x83d2f293, 0xbfa4784b, 0xcbed606e` — это тестовый вектор из pcg-c.

## 6. Тик и цена по CPU

- Фиксированный шаг: `ticksPerSecond = 10` на скорости ×1. Партия 40 минут = 24 000 тиков.
- Скорости ×1, ×2, ×4 меняют только число тиков на секунду реального времени, не результат.
- Адаптер в игре копит время в аккумуляторе и делает не больше `maxTicksPerFrame` тиков за кадр. Если не успевает, игра замедляется, а не пропускает тики.
- Бюджет ядра на этом этапе: тик с `DebugPaint` по 64 пикселя ≤ 0,25 мс в headless на ПК разработчика (подсчёт хеша на контрольной точке не в счёт). Этого хватает, чтобы 100 партий по 24 000 тиков уложились примерно в 10 минут. Раннер меряет и пишет это в отчёт.
- Хеш 512×256 байт — один Burst-джоб раз в 600 тиков, цена пренебрежимая.

## 7. Входы и выходы к другим системам

**Отдаёт прототипу:**

- `World`, `Simulation.Step()`, `SystemPipeline`, `ISimSystem` — сюда встанут фронт, экономика, ИИ;
- `CommandQueue`, `CommandType` — сюда добавятся боевые команды;
- `RngStreams` с зарезервированными потоками `MapGen`, `Front`, `Ai`, `Events`;
- `EndReason` — сюда добавятся победа и поражение;
- `IMatchReporter` в раннере — прототип добавит метрики (длина партии, кто победил);
- `DirtyRowMin/Max` — по ним рендер обновляет текстуру.

**Принимает:** строки JSON из `Data/`, сид, команды. Больше ничего, в том числе времени и ввода напрямую.

**Headless-раннер** (`BattlePix.Editor.HeadlessRunner.Run`):

```
Unity -batchmode -nographics -projectPath . \
  -executeMethod BattlePix.Editor.HeadlessRunner.Run \
  -seeds 1-100 -ticks 24000 -out Reports/run_<дата>
```

- Для каждого сида: создать мир, прогнать до `IsOver`, записать сид, тики, финальный хеш, время, мс на тик (среднее и p99), сколько пикселей у каждой нации.
- Пишет `report.json` (все партии) и `report.md` (сводка: сколько партий, сколько упало, общее время, средний и p99 тик).
- Партия, которая бросила исключение, — в отчёт как крах с сидом и стеком, остальные продолжаются.
- Выход через `EditorApplication.Exit(code)`: 0 — всё прошло, 1 — был хоть один крах или расхождение.
- Режим `-replay <файл>`: проигрывает реплей и сверяет каждую контрольную точку. При расхождении печатает первый тик, где хеш разошёлся, и выходит с кодом 1. Если `dataHash` не совпал — предупреждение и выход с кодом 2, если не передан `-ignoreDataHash`.
- Режим `-determinism <сид>`: два прогона одного сида подряд, сравнение всех контрольных точек.
- Перед прогоном раннер печатает версию Unity, сборки и `dataHash`.

## 8. UI

Экран один — `Main.unity`: карта и отладочная панель. UI на UI Toolkit, `PanelSettings`: Scale Mode = Constant Physical Size, Reference DPI = 160. Все кнопки не меньше 44×44 единиц, это примерно 7 мм, как 44 pt на iOS.

**Карта.** Квад с материалом `OwnerPalette`: текстура владельцев 512×256 `R8`, point-фильтр, без мипов; палитра 256×1 `RGBA32` из `nations_debug.json`, индекс 0 — цвет ничьей земли. Шейдер берёт байт владельца и ищет цвет в палитре. Если после тиков `DirtyRowMin >= 0`, адаптер копирует `Owner` в текстуру (`GetPixelData<byte>(0).CopyFrom`) и делает `Apply(false)`, потом сбрасывает dirty-диапазон. 128 КБ на кадр — дёшево; загрузку только изменённой полосы делаем в прототипе, если профайлер покажет нужду.

**Панель (тап):**

- Пауза, ×1, ×2, ×4, «Шаг» (один тик на паузе).
- Сид (поле ввода) и «Новая партия».
- «Сохранить реплей» — пишет файл из раздела 4.5 и показывает путь.
- Строка состояния: сид, тик, последний хеш, тиков в секунду, мс на тик.

**Тап по карте** — плашка с координатами и владельцем пикселя, закрывается тапом мимо. Подсказок по наведению нет нигде.

На Android приложение при потере фокуса ставится на паузу.

## 10. Edge cases

- Сид 0 и `ulong.MaxValue` работают как любые другие.
- Команда на прошедший тик или дальше горизонта — `Enqueue` возвращает отказ, в лог не пишется.
- Две команды одной нации в один тик — применяются по `Seq`.
- Невалидные параметры команды — отклоняется в тике детерминированно, в реплее так же.
- Смена скорости и пауза посреди партии не меняют хеши: проверяется тестом.
- Кадр подвис на 2 секунды — сделано 8 тиков, остальное «догоняется» в следующих кадрах, тики не пропускаются.
- Выход из Play Mode и domain reload — `World.Dispose()` освобождает все `NativeArray`, утечек нет.
- Burst ещё не скомпилирован — результат тот же, только медленнее; хеш не зависит от Burst.
- Реплей от другой версии данных — раздел 7, код выхода 2.
- Папки `Reports/` или `Replays/` нет — создаётся.
- Нечётная ширина или высота в конфиге — разрешена, ядро не предполагает степень двойки.

## 11. Acceptance criteria

Каждый пункт проверяется тестом или командой.

1. Проект открывается в зафиксированной Unity 6 LTS без ошибок консоли; рендерер URP 2D, на камере Pixel Perfect Camera.
2. `BattlePix.Core.asmdef` не ссылается на Game и Editor. Тест `CoreHasNoForbiddenApis` проходит по всем `.cs` в `Core/` и падает, если находит `UnityEngine`, `MonoBehaviour`, `ScriptableObject`, `float`, `double`, `decimal`, `Mathf`, `System.Random`, `DateTime`, `Stopwatch`, `Environment.TickCount`.
3. `Pcg32(42, 54)` выдаёт эталонные шесть чисел из раздела 5.2.
4. Пример тика из 5.2 воспроизводится тестом: пиксель 128 143 = 3 после тика 1, пиксель 121 794 = 6 после тика 2, `state` потока `Debug` после тика 1 = `0xabc2017ac9febb95`.
5. Один сид, 24 000 тиков, два прогона — все контрольные хеши равны. Сиды 1 и 2 дают разные финальные хеши.
6. Партия с 200 случайными `DebugSetOwner` из лога, проигранная через `-replay`, совпадает на всех контрольных точках. Если подменить одну команду, раннер называет первый расходящийся тик.
7. Одинаковый лог команд на скоростях ×1 и ×4 в игре и в headless даёт одинаковый финальный хеш (реплей, сохранённый из игры, проходит `-replay`).
8. `HashJob` (Burst) и `HashManaged` дают одинаковый хеш на 10 случайных мирах.
9. `-seeds 1-100 -ticks 24000` завершается с кодом 0, пишет `report.json` со 100 записями и `report.md`; средний тик ≤ 0,25 мс. Если не укладывается, это фиксируется в отчёте, и агент не подгоняет цифры.
10. Искусственное исключение в одной партии — отчёт содержит крах с сидом и стеком, остальные 99 партий есть, код выхода 1.
11. EditMode-тесты идут с `NativeLeakDetection` = Enabled With Stack Trace, предупреждений об утечках ноль.
12. В сцене `Main` карта 512×256 рисуется одним рендерером; при запущенной симуляции пиксели меняются; число `Renderer` в сцене ≤ 3.
13. Все кнопки панели ≥ 44×44 единиц в `PanelSettings` из раздела 8; все действия доступны тапом, тап по карте показывает пиксель и владельца.
14. Игра на ПК в 1080p держит 60 fps на скорости ×4 (Unity Profiler, скриншот или числа в PR).
15. В корне лежит CLAUDE.md с разделами из приложения A, в нём записаны версия Unity и команда раннера.

## 12. Out of scope

Генерация континента, фронт и пограничные пиксели, золото, армии, крепости, столицы, войны, ИИ и характеры, победа и поражение, сохранение партии (кроме реплея), загрузка только изменённой полосы текстуры, сборка под Android и проверка детерминизма между платформами, CI, локализация, арт, звук, Entities. Всё это придёт со своими спеками.

## Приложение A. Черновик CLAUDE.md для репо

```markdown
# BattlePix

Стратегия за одну нацию на пиксельной карте. Партия 30–40 минут. Unity <версия LTS>, URP 2D. ПК (Steam) первым, мобилка портом.

## Пиллары — фича, которая не усиливает ни один, режется
1. Живой фронт: граница двигается в реальном времени, результат решения виден на карте.
2. Решение — выбор с ценой: 2–5 вариантов, у каждого своя плата, слайдеров нет.
3. Короткая партия: 30–40 минут, всегда есть конец.

## Правила ядра (нарушение = переделка)
- `Assets/BattlePix/Core` — чистый C#. Нельзя: UnityEngine.*, MonoBehaviour, ScriptableObject, сцена, float/double/decimal, Mathf, System.Random, DateTime, Stopwatch. Можно: Unity.Collections, Unity.Jobs, Unity.Burst, Unity.Mathematics (целые типы).
- Вся случайность — через `RngStreams`, у каждой системы свой поток. Номера потоков не менять, только дописывать.
- Мир меняется только командами из `CommandType`. Игрок и ИИ пользуются одним списком. Отдельный ИИ не пишем: ИИ — характер, который выбирает команды по весам из данных.
- Команды из UI ставятся на следующий тик.
- Порядок обработки фиксирован, никаких итераций по Dictionary/HashSet там, где важен порядок.
- Горячие циклы — Burst-джобы, пишут в непересекающиеся индексы. Фронт считается только по пограничным пикселям.
- Рендер только читает мир между тиками. Одна Texture2D владельцев + палитра в шейдере, никаких GameObject на пиксель.
- Нации, характеры, цели войны, рельеф, баланс — в `Assets/StreamingAssets/Data/*.json`, не в коде.
- UI — только тап, цели ≥ 44×44, никаких подсказок по наведению.

## Как проверять
- Тесты: Test Runner → EditMode, или `Unity -batchmode -runTests -testPlatform EditMode -projectPath .`
- 100 бот-партий: `Unity -batchmode -nographics -projectPath . -executeMethod BattlePix.Editor.HeadlessRunner.Run -seeds 1-100 -ticks 24000 -out Reports/run`
- Баг = сид + реплей. Проверка: `... -executeMethod BattlePix.Editor.HeadlessRunner.Run -replay <файл>`
- Любое изменение ядра: тесты зелёные, `-determinism 42` проходит, бюджет тика в отчёте не вырос без причины.

## Как работаем
- Каждая механика: бриф → спека → реализация → 100 бот-партий → плейтест → вердикт.
- Делай ровно то, что в спеке. Новое — только с ответом «что это вытесняет», иначе в бэклог.
- Баланс меняется в данных и проверяется бот-прогоном, не на глаз.
- Спеки лежат в `docs/specs/`. Текущий этап: 0 «Фундамент».
```
